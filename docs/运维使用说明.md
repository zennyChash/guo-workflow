# guo-workflow 运维使用说明

> 文档版本：第一个可交付里程碑<br>
> 适用对象：流程实施、系统运维、流程配置和业务运营人员

## 1. 文档目的

本说明用于指导运维人员完成以下工作：

- 阅读和维护带 `guo` 扩展标签的审批流程定义；
- 配置单人审批、会签、或签、退回、通知和业务动作；
- 查询运行中的流程、待办、审批轨迹和异步任务；
- 了解数据库和租户等运行配置；
- 快速判断常见异常，并安全执行查询或补处理。

`guo` 标签用于简化审批语义。正式发布时，系统会将 `guo` 审批语义转换为可运行的流程定义，并删除部署定义中的 `guo` 审批扩展；原始配置和语义快照会保存在流程定义目录中。

业务动作不直接写入节点定义，而是按“流程定义版本 + 环节 + 触发范围 + 事件”从动作配置表读取。

## 2. 基本概念

| 名称 | 含义 |
| --- | --- |
| 流程 Key | 一个业务流程的稳定编码，例如 `purchaseApproval` |
| 流程定义版本 | 同一流程 Key 每次正式发布后形成的新版本 |
| 流程实例 | 某张业务单据实际发起后的一次流程 |
| 业务主键 | 关联业务单据的稳定编号，例如订单号或采购申请号 |
| 环节 ID | 流程节点 ID，例如 `departmentApproval` |
| 任务 ID | 某位审批人实际收到的一条待办 |
| 租户 ID | 数据隔离标识；空值表示无租户 |
| 动作 | 环节生命周期上执行的校验、业务处理、消息或导出 |
| 流程镜像 | 为查询和看板准备的扁平业务数据，不需要解析底层流程表 |

### 2.1 两种变量写法

配置中有两种容易混淆的写法：

| 写法 | 用途 | 示例 |
| --- | --- | --- |
| `${...}` | 流程运行表达式，常用于审批人集合或流程变量选择 | `approvers="${financeApprovers}"` |
| `#{...}` | guo 动作和消息模板占位符，运行前替换为实际值 | `#{businessKey}` |
| `#{$attrs.xxx}` | 从动作属性中取值 | `#{$attrs.operation}` |

`#{...}` 占位符无法解析时会报错，不会静默替换为空字符串。

### 2.2 常用核心字段

以下字段可直接用于动作和消息模板：

| 字段 | 含义 |
| --- | --- |
| `businessKey` | 当前流程业务主键 |
| `processDefinitionKey` | 流程 Key |
| `processInstanceId` | 流程实例 ID |
| `taskId` | 当前任务 ID |
| `activityId` | 当前环节 ID |
| `initiator` | 发起人 |
| `startUserId` | 发起人用户 ID |
| `tenantId` | 租户 ID |
| `currentApprover` | 当前会签审批人 |
| `operatorId` | 当前任务办理人，完成任务时可使用 |
| `currentActivityName` | 当前环节名称，节点整体完成时可使用 |

退回和取消补偿动作还可使用：

| 属性 | 含义 |
| --- | --- |
| `#{$attrs.operation}` | `RETURN` 表示退回，`CANCEL` 表示取消 |
| `#{$attrs.returnTargetActivityId}` | 退回目标环节 ID，取消时为空 |

## 3. guo 审批标签总览

使用时需要在流程定义根节点声明 `guo` 命名空间：

```xml
xmlns:guo="http://guo.workflow/schema/approval"
```

审批扩展放在审批节点的 `extensionElements` 中：

```xml
<userTask id="financeApproval" name="财务审批">
  <extensionElements>
    <guo:approval mode="SINGLE" approvers="${financeApprover}">
      <!-- 可选：允许退回的目标 -->
      <guo:return to="departmentApproval" />

      <!-- 可选：通知 -->
      <guo:notification trigger="assignment"
                        channel="dingtalk"
                        to="#{currentApprover}">
        <guo:title>待办提醒</guo:title>
        <guo:content>业务 #{businessKey} 待您审批</guo:content>
      </guo:notification>
    </guo:approval>
  </extensionElements>
</userTask>
```

每个审批节点最多配置一个 `guo:approval`。

XML 中不能直接写未转义的 `<`、`>` 和 `&`。SQL、脚本等长文本建议放在 CDATA 中：

```xml
<script><![CDATA[
  return price > cost && price > 0
]]></script>
```

不便使用 CDATA 时，应分别写成 `&lt;`、`&gt;`、`&amp;`。

### 3.1 `guo:approval` 属性

| 属性 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `mode` | 否 | `SINGLE` | 审批模式：`SINGLE`、`OR_SIGN`、`COUNTERSIGN` |
| `approvers` | 是 | 无 | 审批人或审批人集合表达式；未填写时兼容读取 `flowable:assignee` |
| `sequential` | 否 | `false` | 仅会签使用；`true` 为顺序会签，`false` 为并行会签 |
| `completionPolicy` | 否 | `ALL` | 仅会签使用：`ALL`、`ANY`、`PERCENTAGE` |
| `threshold` | 条件必填 | 无 | 仅 `PERCENTAGE` 使用，取值大于 0 且不超过 1 |
| `commentRequired` | 否 | `false` | 表示业务上要求审批意见；当前版本仅保存语义，由调用端校验 |
| `rejectPolicy` | 否 | 无 | 保存驳回策略描述；当前版本不会根据该值自动跳转 |

### 3.2 审批模式

| 模式 | 运行效果 | 典型场景 |
| --- | --- | --- |
| `SINGLE` | 生成一个指定处理人的任务 | 部门负责人、财务负责人单审 |
| `OR_SIGN` | 生成一个多人候选任务，首位领取并完成的人代表该环节通过 | 值班审批、任一负责人处理 |
| `COUNTERSIGN` | 按人员集合生成多个会签任务 | 多人会签、财务联签 |

需要区分 `OR_SIGN` 和会签 `ANY`：

- `OR_SIGN` 只有一个公共任务，谁先领取谁处理；
- `COUNTERSIGN + ANY` 会为每个人生成任务，只要第一个人完成，环节即完成，其余任务失效。

### 3.3 会签完成策略

| 策略 | 说明 |
| --- | --- |
| `ALL` | 所有人完成后环节完成 |
| `ANY` | 任意一人完成后环节完成 |
| `PERCENTAGE` | 完成人数达到指定比例后环节完成 |

比例会签示例：

```xml
<guo:approval mode="COUNTERSIGN"
              sequential="false"
              completionPolicy="PERCENTAGE"
              threshold="0.67"
              approvers="${financeApprovers}" />
```

上述配置表示至少三分之二的审批人完成后，会签节点结束。

### 3.4 `guo:return` 子节点

`guo:return` 声明当前环节允许退回到哪些节点。

```xml
<guo:return to="departmentApproval,firstApproval" />
```

| 属性 | 必填 | 说明 |
| --- | --- | --- |
| `to` | 是 | 逗号分隔的允许退回目标环节 ID |
| `targets` | 否 | `to` 的兼容别名，推荐统一使用 `to` |

规则：

- 目标必须是同一流程中已存在的审批用户任务；
- 不能退回当前节点自身；
- 未配置 `guo:return` 的节点不允许退回；
- 目标重复时会自动去重；
- 退回到发起人、开始事件或任意历史节点目前不支持；
- 是否存在退回按钮、哪些角色可选择哪个目标，由界面按该白名单控制。

### 3.5 `guo:notification` 子节点

一个审批节点可配置多条通知，每条通知对应一个渠道。

| 属性 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `trigger` | 是 | 无 | 通知触发时机 |
| `channel` | 是 | 无 | 消息渠道，例如 `dingtalk`、`wecom` |
| `to` | 是 | 无 | 接收人，支持逗号分隔 |
| `format` | 否 | `text` | `text` 或 `markdown` |

子节点：

| 子节点 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 否 | 消息标题 |
| `content` | 是 | 消息正文 |

`trigger` 可用值：

| 值 | 含义 |
| --- | --- |
| `todo`、`assigned`、`assignment` | 待办产生或转办后通知 |
| `submitted`、`task-complete`、`task-completed` | 单个会签人提交后通知 |
| `node-complete`、`node-completed`、`completed` | 会签节点整体完成后通知 |

普通单人或或签节点配置 `node-complete` 时，系统会自动按单个任务完成处理。

通知属于业务动作，未配置通知时不会发送消息。异步重试可能造成重复通知，渠道实现应尽量使用业务键或动作 ID 保证幂等。

### 3.6 当前限制

以下能力当前请在配置中避开：

- `completionPolicy="VETO"` 会在发布校验时被拒绝；
- 动态加签、减签暂不支持；
- `rejectPolicy` 和 `commentRequired` 当前只保存语义，不会自动改变流程或强制校验意见；
- `guo:return` 只定义可选择目标，实际退回由办理操作触发；
- 暂不支持退回至发起人或开始事件。

## 4. 常见配置示例

以下示例互相独立，可按实际流程选择。

### 4.1 并行三人会签，允许退回部门审批

```xml
<userTask id="financeCountersign" name="财务会签">
  <extensionElements>
    <guo:approval mode="COUNTERSIGN"
                  sequential="false"
                  completionPolicy="ALL"
                  approvers="${financeApprovers}">
      <guo:return to="departmentApproval" />

      <guo:notification trigger="assignment"
                        channel="dingtalk"
                        to="#{currentApprover}">
        <guo:title>财务会签待办</guo:title>
        <guo:content>业务 #{businessKey} 等待您完成财务会签。</guo:content>
      </guo:notification>

      <guo:notification trigger="node-complete"
                        channel="wecom"
                        to="#{initiator}">
        <guo:content>业务 #{businessKey} 的财务会签已全部完成。</guo:content>
      </guo:notification>
    </guo:approval>
  </extensionElements>
</userTask>
```

调用发起操作时，`financeApprovers` 应为审批人 ID 集合，例如：

```text
financeApprovers = ["finance-a", "finance-b", "finance-c"]
```

配置要点：

- 三名人员会同时收到任务；
- 三人全部完成后会签节点结束；
- 任一会签任务发起退回时，当前会签节点剩余任务会全部失效，再产生一条部门审批新任务；
- 再次进入会签时，会重新发起一整轮会签。

### 4.2 顺序会签，三分之二通过

```xml
<userTask id="managerCountersign" name="经理会签">
  <extensionElements>
    <guo:approval mode="COUNTERSIGN"
                  sequential="true"
                  completionPolicy="PERCENTAGE"
                  threshold="0.67"
                  approvers="${managerApprovers}" />
  </extensionElements>
</userTask>
```

例如审批人集合有 3 人，完成 2 人后节点结束。已完成的 2 人按顺序产生任务，后一人只在前一人完成后收到待办。

### 4.3 或签：任意销售负责人处理

```xml
<userTask id="salesReview" name="销售负责人审核">
  <extensionElements>
    <guo:approval mode="OR_SIGN"
                  approvers="${salesApprovers}">
      <guo:notification trigger="assignment"
                        channel="dingtalk"
                        to="#{salesManagerIds}">
        <guo:content>有一笔销售审批等待负责人处理，业务号 #{businessKey}。</guo:content>
      </guo:notification>
    </guo:approval>
  </extensionElements>
</userTask>
```

运行规则：

- 生成一条公共候选任务；
- 任意候选人领取后成为处理人；
- 该任务完成后环节结束；
- 未领取前不会自动分配给某一个人。

示例中的 `salesManagerIds` 应是逗号分隔的字符串。不要把审批人集合直接作为 `to`
使用，否则可能得到类似 `[a, b]` 的文本。

### 4.4 一票否决：任一人驳回时立即整体退回

当前版本不要配置 `completionPolicy="VETO"`。可以通过“会签 + 白名单退回”实现同样的一票否决效果：

```xml
<userTask id="riskCountersign" name="风控会签">
  <extensionElements>
    <guo:approval mode="COUNTERSIGN"
                  sequential="false"
                  completionPolicy="ALL"
                  approvers="${riskApprovers}">
      <guo:return to="initiatorApproval" />
    </guo:approval>
  </extensionElements>
</userTask>
```

前端处理规则：

1. 审批人点击“同意”时，正常完成任务；
2. 审批人点击“驳回”时，调用退回操作；
3. 退回请求包含当前任务 ID、目标环节 `initiatorApproval` 和驳回意见；
4. 系统取消当前风控会签节点的所有活动任务；
5. 当前节点配置为 `event="delete"` 的补偿动作执行；
6. 流程迁移到目标节点并记录审批意见。

退回操作的业务参数：

| 参数 | 说明 |
| --- | --- |
| 当前任务 ID | 选择驳回的审批人任务 |
| 目标环节 ID | 必须是 `guo:return` 白名单中的值 |
| 驳回意见 | 写入审批意见并进入审批轨迹 |

这种方案下，第一位驳回人即可终止当前会签节点。不能直接操作数据库修改任务状态来代替退回操作。

### 4.5 完成后更新业务单据状态

动作配置示例：

```xml
<actions>
  <action id="approve-order"
          event="complete"
          type="job"
          doType="sql"
          sync="true"
          datasource="biz_db">
    <sql>
      UPDATE t_order
      SET status = 'APPROVED',
          approved_amount = #{approvedAmount}
      WHERE order_no = #{businessKey}
        AND status = 'APPROVING'
    </sql>
  </action>
</actions>
```

规则：

- `#{businessKey}`、`#{approvedAmount}` 会作为预编译参数绑定；
- 不拼接原始文本；
- 必须配置业务数据源 `datasource`；
- 执行异常会阻止当前同步操作，并触发事务回滚；
- 条件中应保留业务状态防断层，例如仅允许审批中的数据被改为已审批。

### 4.6 退回或取消时执行逆向补偿

```xml
<actions>
  <action id="restore-order-on-return"
          event="delete"
          type="job"
          doType="sql"
          sync="true"
          datasource="biz_db">
    <sql>
      UPDATE t_order
      SET status = 'DRAFT'
      WHERE order_no = #{businessKey}
        AND status = 'APPROVING'
        AND shipment_status = 'NONE'
        AND #{$attrs.operation} IN ('RETURN', 'CANCEL')
    </sql>
  </action>
</actions>
```

注意事项：

- 补偿动作配置在发起退回或取消的当前节点；
- 条件应判断当前业务状态，避免撤销已经进入后续业务阶段的单据；
- 同一动作可能因取消和退回被触发，需要时可用 `#{$attrs.operation}` 区分；
- 补偿 SQL 本身仍需保证幂等。

### 4.7 提交前校验

脚本校验：

```xml
<actions>
  <action id="check-profit"
          event="complete"
          type="validate"
          doType="script"
          sync="true">
    <script><![CDATA[
      // price、cost 直接来自流程变量。
      return price != null && cost != null && price > 0
             && (price - cost) / price >= 0.05
    ]]></script>
    <error-msg>销售毛利率不得低于 5%</error-msg>
  </action>
</actions>
```

SQL 校验：

```xml
<actions>
  <action id="check-credit"
          event="complete"
          type="validate"
          doType="sql"
          sync="true"
          datasource="biz_db">
    <sql>
      SELECT available_amount >= #{orderAmount}
      FROM t_credit
      WHERE customer_id = #{customerId}
    </sql>
    <error-msg>客户可用信用额度不足</error-msg>
  </action>
</actions>
```

SQL 校验取第一行第一列：

- 布尔 `true` 通过；
- 非 0 数值通过；
- `false`、`0`、空值或不通过时抛出 `error-msg`。

校验动作不使用 `<result var="..."/>`，校验结果只决定通过或失败。

### 4.8 调用存储过程

```xml
<actions>
  <action id="reserve-stock"
          event="complete"
          type="job"
          doType="stored_proc"
          sync="true"
          datasource="erp_db">
    <proc name="pkg_order.reserve_stock">
      <in value="#{businessKey}" type="VARCHAR" />
      <in value="#{warehouseId}" type="VARCHAR" />
      <out resultVar="reserveCode" type="INTEGER" />
      <out resultVar="reserveMessage" type="VARCHAR" />
    </proc>
  </action>
</actions>
```

`in`、`out` 的 XML 顺序就是过程参数的顺序。常用类型包括：

```text
VARCHAR, CHAR, LONGVARCHAR, INTEGER, SMALLINT, TINYINT, BIGINT,
DECIMAL, NUMERIC, DOUBLE, FLOAT, BOOLEAN, DATE, TIMESTAMP, BLOB, CLOB,
CURSOR
```

需要同时接收结果集和输出参数时：

```xml
<proc name="p_process_order"
      resultSet="true"
      resultVar="orderDetails">
  <in value="#{businessKey}" type="VARCHAR" />
  <out resultVar="statusCode" type="INTEGER" />
</proc>
```

说明：

- `resultSet="true"` 时，返回结果集写入 `resultVar`，未配置 `resultVar` 时写入 `<环节ID>_proResult`；
- OUT 参数同时按各自 `resultVar` 写入；
- MySQL 推荐使用 `resultSet="true"`，不要依赖 `CURSOR`；
- `CURSOR` 适用于支持游标输出的数据库。

### 4.9 发送多渠道消息

```xml
<actions>
  <action id="notify-approval-result"
          event="complete"
          type="job"
          doType="message"
          sync="false">
    <message channel="dingtalk"
             to="#{salesOwner},#{$attrs.financeManagerId}"
             format="markdown">
      <title>审批完成</title>
      <content>业务 #{businessKey} 已审批完成，金额 #{orderAmount}。</content>
    </message>
    <message channel="wecom"
             to="#{warehouseOwner}"
             format="text">
      <content>请安排业务 #{businessKey} 的后续发货。</content>
    </message>
  </action>
</actions>
```

同一个动作中的多条消息会并行发送，任一渠道失败都会使动作失败，并按异步任务规则重试。

### 4.10 调用宿主业务操作生成关联单据

```xml
<actions>
  <action id="create-purchase-draft"
          event="complete"
          type="job"
          doType="business"
          sync="false">
    <business actionKey="erp.purchaseOrder.createDraft" version="1">
      <param name="purchaseApplicationId" value="#{businessKey}" />
      <param name="targetWarehouseId" value="#{targetWarehouseId}" />
      <param name="approvedAmount"
             value="#{approvedAmount}"
             type="decimal" />
    </business>
  </action>
</actions>
```

`param` 属性：

| 属性 | 必填 | 说明 |
| --- | --- | --- |
| `name` | 是 | 传给业务操作的参数名 |
| `value` | 是 | 变量、属性或混合文本 |
| `type` | 否 | `string`、`int`、`long`、`decimal`、`boolean` |
| `required` | 否 | 默认 `true`；可选参数取不到时不传给业务操作 |

业务操作成功后，关联单据 ID、类型、标题、链接会写入业务关联表，并保留稳定幂等键。

业务数据库和流程主库不是同一套强一致事务。同步补偿动作失败会阻止流程继续，但已经
单独提交的业务库修改只能按业务对冲原则补偿，因此配置时必须包含状态校验和幂等条件。

### 4.11 提交文件导出任务

```xml
<actions>
  <action id="export-order-detail"
          event="complete"
          type="job"
          doType="export"
          sync="false">
    <target fileType="xlsx"
            expTaskId="purchase_order_detail_export" />
  </action>
</actions>
```

`fileType` 和 `expTaskId` 必填。`expTaskId` 是导出模块中的任务定义 ID。

导出成功后会写入两个流程变量：

```text
exportTicket_<环节ID>_<动作ID>      导出模块返回的凭据号
exportUniqueBizKey_<环节ID>_<动作ID> 稳定幂等业务键
```

建议为导出动作配置稳定的 `id`，否则自动生成的 ID 不利于人工排查。

## 5. 动作配置参考

### 5.1 动作 XML 根结构

```xml
<actions>
  <action id="稳定动作ID"
          event="complete"
          type="job"
          doType="sql"
          sync="true"
          phase="before-commit"
          datasource="biz_db">
    <!-- 具体执行内容 -->
  </action>
</actions>
```

### 5.2 `action` 属性

| 属性 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 建议 | 稳定动作 ID；用于幂等键、导出变量和排查 |
| `event` | 是 | 触发事件 |
| `type` | 是 | `validate` 或 `job` |
| `doType` | 是 | `sql`、`script`、`stored_proc`、`message`、`export`、`business` |
| `sync` | 否 | 默认 `true`；`true` 在当前请求内执行，`false` 写入异步任务 |
| `phase` | 否 | `before-commit` 或 `after-commit` |
| `datasource` | 条件必填 | SQL 和存储过程必须配置业务数据源名称 |

### 5.3 `type` 与 `doType`

| `type` | 允许的 `doType` | 语义 |
| --- | --- | --- |
| `validate` | `sql`、`script` | 前置校验；必须同步且在提交前执行 |
| `job` | 全部六种 | 业务任务；可同步或异步 |

当前限制：

- `validate + stored_proc` 尚无可用执行入口，请勿配置；
- `validate` 不允许 `sync="false"`；
- `validate` 不允许 `phase="after-commit"`；
- 业务型存储过程应使用 `job + stored_proc`。

### 5.4 触发事件

| 事件 | 当前用途 |
| --- | --- |
| `create` | 任务创建；流程节点需显式挂载通用动作监听器 |
| `assignment` | 任务分配或转办 |
| `complete` | 任务完成 |
| `delete` | 任务删除、退回或业务取消 |
| `take` | 当前版本保留，尚无可用的通用触发入口 |

标准退回和业务取消统一使用 `event="delete"`，不要配置 `event="return"` 或 `event="rollback"`。

由 `guo:approval` 编译生成的审批节点默认接入 `assignment`、`complete` 和 `delete`。
没有 `guo:approval` 的普通节点如需这些事件，应在流程定义中显式配置通用动作监听器。

### 5.5 同步与异步

| 配置 | 执行方式 |
| --- | --- |
| `sync="true"` | 在流程操作事务内执行；失败会阻止流程继续 |
| `sync="false"` | 写入异步任务表，提交后由后台消费者执行 |

推荐：

- 强校验、业务数据强一致更新、逆向补偿使用 `sync="true"`；
- 消息、导出、可重试的外部系统调用使用 `sync="false"`；
- 当前版本不建议配置 `sync="true"` 且 `phase="after-commit"` 的组合。

### 5.6 占位符规则

SQL、消息模板和业务参数支持：

```text
#{amount}                 先取流程变量 amount
#{businessKey}            取核心字段
#{$attrs.tenantId}        取动作上下文属性
```

流程变量不存在时再尝试核心字段；仍不存在则报错。

SQL 的 `#{}` 会转换为预编译参数，不应自行拼接用户输入。

### 5.7 脚本上下文

脚本中：

- 流程变量直接使用变量名，例如 `price`、`customerName`；
- 系统属性通过 `$attrs.tenantId` 获取；
- 核心字段还包括 `businessKey`、`processInstanceId`、`taskId`、`activityId`。

脚本语言使用 `lang="groovy"` 或 `lang="js"`。未写时默认 Groovy。

业务任务脚本的结果写入：

```xml
<result var="nextApprover" />
```

未配置 `<result>` 时默认写入 `scriptResult`。

### 5.8 SQL 结果回写

普通增删改：

```xml
<sql>
  UPDATE t_order SET status = 'APPROVED' WHERE order_no = #{businessKey}
</sql>
```

需要把第一行第一列写入流程变量时：

```xml
<sql>
  SELECT next_approver
  FROM t_task_rule
  WHERE dept_id = #{deptId}
    AND amount &gt;= #{amount}
</sql>
<result var="nextApprover" />
```

查询无结果时写入 `null`。分页类限制使用 `maxRows` 或 `max-rows`，不要写数据库专用分页语句。

### 5.9 动作配置定位

动作配置保存在 `t_node_action_config`，新配置按以下四项定位：

```text
process_definition_id + activity_id + trigger_scope + event
```

`trigger_scope`：

| 值 | 说明 |
| --- | --- |
| `TASK` | 单个任务事件 |
| `NODE` | 会签节点整体完成事件 |
| `PROCESS` | 预留，当前没有通用触发入口 |

旧配置中 `process_definition_id` 为空时，可按 `process_definition_key` 作为兼容配置读取。

## 6. 日常办理操作

### 6.1 发起流程

发起时至少准备：

| 参数 | 说明 |
| --- | --- |
| 流程 Key | 要发起的流程 |
| 操作人 | 当前发起人 |
| 租户 ID | 可为空；有租户时必须与已发布流程匹配 |
| 业务变量 | 包含业务主键字段 |
| 审批人集合 | 会签或或签所需的用户 ID 集合 |

系统会自动补充 `businessKey`、`initiator`、`startUserId`、`tenantId`。

### 6.2 待办处理

标准操作顺序：

1. 查询当前用户待办；
2. 对公共候选任务执行领取；
3. 审批完成后填写意见和业务变量；
4. 完成任务；
5. 需要时转办或退回领取。

完成或转办后的操作人会进入动作上下文，可在消息模板中使用 `#{$attrs.operatorId}`。

### 6.3 退回

退回应使用当前任务、允许目标环节和意见，不允许任意传入前置节点。

退回后的历史记录：

- 当前活动任务变为 `DELETED`；
- 审批轨迹写入 `DELETE` 和意见；
- 目标节点生成新任务；
- 会签节点重走时重新建立完整一轮待办。

### 6.4 取消

业务取消会终止流程实例并保留历史轨迹，最终流程状态为 `CANCELLED`。

取消与“删除流程数据”不同。禁止通过手工删除流程镜像或历史表来处理业务取消。

## 7. 配置说明

### 7.1 主数据库

生产环境建议通过环境变量或运行目录下的外部 `config/application-local.yml` 提供：

```yaml
spring:
  datasource:
    url: ${WORKFLOW_DB_URL}
    username: ${WORKFLOW_DB_USERNAME}
    password: ${WORKFLOW_DB_PASSWORD}
    driver-class-name: ${WORKFLOW_DB_DRIVER}
    hikari:
      maximum-pool-size: 10
      minimum-idle: 2
      connection-timeout: 30000
```

数据库账号至少需要：

- 流程运行、镜像表、动作配置表和异步任务表的读写权限；
- 查询业务流程所需的只读权限；
- 执行已批准存储过程的权限。

生产环境不要把真实密码写入源码目录。

流程内核结构自动更新开关：

```yaml
flowable:
  database-schema-update: ${FLOWABLE_SCHEMA_UPDATE:true}
  check-process-definitions: false
```

首次部署时应先确认结构初始化结果；已有生产库完成受控升级后，建议明确设置为
`false`，避免启动时自动修改结构。`check-process-definitions: false` 表示不自动
扫描本地流程文件，流程通过发布操作统一管理。变更前必须备份。

### 7.2 业务数据库

业务 SQL 和存储过程通过 XML 的 `datasource` 属性选择业务库。

推荐由宿主在运行时注册同名业务数据源。开发环境可允许流程引擎根据以下配置创建：

```yaml
guo:
  workflow:
    datasources:
      auto-create: true
      definitions:
        biz_db:
          url: ${BIZ_DB_URL}
          username: ${BIZ_DB_USERNAME}
          password: ${BIZ_DB_PASSWORD}
          driver-class-name: ${BIZ_DB_DRIVER}
          maximum-pool-size: 10
          minimum-idle: 2
          connection-timeout-ms: 30000
```

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `auto-create` | `false` | 是否允许引擎根据配置创建业务数据源 |
| `url` | 无 | 业务库连接地址 |
| `username` | 无 | 业务库用户 |
| `password` | 无 | 业务库密码 |
| `driver-class-name` | 无 | 数据库驱动类 |
| `maximum-pool-size` | `10` | 最大连接数 |
| `minimum-idle` | `2` | 最小空闲连接数 |
| `connection-timeout-ms` | `30000` | 获取连接超时 |

同名业务数据源同时存在时，宿主提供的优先。未配置或未找到数据源时，SQL 和存储过程动作直接失败，不会回退到流程主库。

### 7.3 租户

租户 ID 长度为 64 个字符以内。

租户在三个位置保持一致：

1. 流程定义发布时的租户；
2. 发起流程时的租户；
3. 查询、待办和动作配置查询时的租户。

租户为空的流程只能按空租户查询。不要把空租户和一个具体租户混用。

候选组待办需要宿主把当前用户展开为组 ID。未接入组织解析时，只能可靠显示直接
指派给该用户的任务，以及直接列出的候选用户任务。

### 7.4 消息渠道

```yaml
guo:
  workflow:
    message:
      max-concurrency: 8
      http:
        connect-timeout-seconds: 5
        request-timeout-seconds: 10
      channels:
        dingtalk:
          enabled: true
          webhook: ${DINGTALK_WEBHOOK}
          secret: ${DINGTALK_SECRET}
          recipient-type: user-id
        wecom:
          enabled: true
          webhook: ${WECOM_WEBHOOK}
          recipient-type: user-id
```

| 配置 | 说明 |
| --- | --- |
| `max-concurrency` | 单个消息动作内最多并行发送的渠道数 |
| `http.connect-timeout-seconds` | 建立连接超时 |
| `http.request-timeout-seconds` | 完整请求超时 |
| `enabled` | 是否启用内置群机器人渠道 |
| `webhook` | 群机器人地址 |
| `secret` | 钉钉签名密钥，企业微信不需要 |
| `recipient-type` | `user-id` 或 `mobile` |

内置钉钉和企业微信渠道面向群机器人，`to` 表示在群内提及用户，不负责企业应用向个人直发。按应用身份直发时应由宿主提供自定义渠道。

### 7.5 异步任务

```yaml
guo:
  workflow:
    fetch-size: 10
    async:
      core-pool-size: 2
      max-pool-size: 4
      queue-capacity: 100
      retry-base-seconds: 2
      retry-max-delay-seconds: 300
      jitter-ratio: 0.2
      processing-timeout-seconds: 600
```

| 配置 | 说明 |
| --- | --- |
| `fetch-size` | 每次拉取任务数 |
| `core-pool-size` | 常规并发线程数 |
| `max-pool-size` | 最大并发线程数 |
| `queue-capacity` | 等待队列长度 |
| `retry-base-seconds` | 首次重试基础延迟 |
| `retry-max-delay-seconds` | 最大重试延迟 |
| `jitter-ratio` | 重试随机抖动比例 |
| `processing-timeout-seconds` | 超时任务重新放回待处理的阈值 |

处理超时的任务会被恢复为 `PENDING`，因此业务动作必须按业务主键或动作 ID 保证幂等。

### 7.6 服务端口

```yaml
server:
  port: ${SERVER_PORT:8080}
```

健康检查：

```text
GET /actuator/health
```

## 9. 常用运维查询

以下示例使用租户 `T001`，执行时请替换为实际值。

### 9.1 按业务主键查询流程

```sql
SELECT process_instance_id,
       process_definition_key,
       process_definition_version,
       process_name,
       process_status,
       active_task_count,
       current_node_names,
       current_handler_names,
       start_time,

人工重新投递 `DEAD` 任务前，必须确认动作幂等性和外部系统状态。确认允许重试后，可由运维流程执行：

    claim_token = NULL,
    next_retry_time = NULL,
    error_msg = NULL,
    update_time = CURRENT_TIMESTAMP

  AND status = 'DEAD';
```

不要直接修改 `PROCESSING` 任务，除非已经确认执行节点失联并超过处理超时时间。

## 11. 故障排查

### 11.1 待办中看不到人员

检查：

1. `approvers` 表达式是否能得到有效用户 ID 集合；
2. 用户是否有直接候选资格或所属候选组；
3. 查询租户是否与发起租户一致；
4. 任务是否已经由其他人领取；
5. 流程是否仍在运行。

### 11.2 无法完成任务

常见原因：

- 当前用户不是任务处理人；
- 公共候选任务尚未领取；
- 提交前校验没有通过；
- 同步业务动作执行失败；
- 补偿动作条件不满足；
- 任务已被退回、取消或其他操作删除。

### 11.3 消息没有发送

检查：

1. 是否配置了通知；
2. 渠道是否启用；
3. `webhook` 是否正确；
4. `to` 替换后是否为空；
5. 异步任务是否进入 `RETRY_WAIT` 或 `DEAD`；
6. 群机器人是否允许当前发送地址。

### 11.4 业务 SQL 失败

检查：

- `datasource` 名称是否存在；
- 业务库账号权限；
- SQL 占位符变量是否存在；
- 是否违反业务唯一约束；
- 状态防断层条件是否导致更新 0 行；
- 是否误用了流程主库。

### 11.5 任务长期停留在 PROCESSING

后台会按 `processing-timeout-seconds` 自动恢复超时任务。恢复后会再次执行，因此动作必须幂等。

如大量任务长期为 `PROCESSING`，优先排查执行线程是否耗尽、外部系统是否阻塞，以及应用是否频繁重启。

## 12. 当前版本能力边界

已支持：

- 单人或签、并行/顺序会签、或签；
- `ALL`、`ANY`、`PERCENTAGE` 完成策略；
- 受控退回和业务取消；
- 显式配置的待办、提交完成、节点完成通知；
- SQL、脚本、存储过程、业务操作、消息和导出动作；
- 同步校验和异步可靠任务；
- 流程镜像、审批轨迹和业务关联查询；
- 租户和操作人上下文。

暂不支持或仅保留：

- `VETO` 静态配置；
- 动态加签、减签；
- 退回至发起人或任意历史节点；
- 通用 `take` 事件动作；
- 通用 `PROCESS` 范围动作；
- 业务校验型存储过程；
- `commentRequired` 的强制意见校验；
- `rejectPolicy` 的自动跳转。

一票否决可按 4.4 节的“会签 + 受控退回”方式实现。涉及动态参与人、反复加减签或复杂投票计数的需求，应先确认客户场景后再扩展。
